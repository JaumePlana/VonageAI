My recommendation: work out how the Interaction Plans Architect page loads and saves plans, then pick the method based on what we find. Whatever we pick, keep a common plan format in the middle, so that changing method later only affects one part of the code.

Step 1: Watch what the Architect page sends (about an hour, read-only)

In the Test account, open the browser's developer tools on the Network tab, then:
1. Open a simple existing plan in the Architect.
2. Add one Announcer applet, change a setting, save.
3. Export the network log as a HAR file (Network tab → right-click → "Save all as HAR").

Save it under exports/, which git ignores. Don't send it anywhere: a HAR contains your login cookies and tokens. I'll write a small script that strips them before we look inside.

The log will show which of two cases we're in:
- A. The page loads and saves the plan as JSON through a backend API (most likely for a modern web app). We get the full applet structure, both for reading and for writing.
- B. The page doesn't use a clean API. For example, it sends a lot of HTML or does many small calls per click.

Step 2: Choose how to build

- If A: call those same backend endpoints from Python, using your own logged-in browser session.
  - Python gets the session by having Playwright open a browser once and reuse your login, so SSO and MFA still work.
  - It's fast, does exactly what the page does, and copying a plan becomes "read JSON from Test, swap the account-specific IDs, write the JSON to PROD".
  - Safeguards, since the endpoints are undocumented:
    - Every write gets a dry-run preview first.
    - After each write we read the plan back and compare.
    - Tests catch it if Vonage changes the format.
    - Nothing touches PROD until a full Test → Test copy works.
- If B: automate the Architect page itself with Playwright, clicking through it as you would. It's slower and needs fixing when the UI changes, but it works.

Step 3: A common plan format

Define one plain JSON format for a plan: its applets, their settings, the connections between them, and references to groups, skills and transfer strings stored as names rather than account IDs. Then:
- Copy Test → PROD: read the plan from Test into this format, translate names to PROD's IDs (looked up through the APIs that work), then write it to PROD.
- DrawIO/Visio → VCC: convert the diagram to the same format. Claude is useful here for interpreting messy drawings, and you review the result before anything is built.

The code we have now still has a job: logging in, listing plans, creating the empty plan and setting up number mappings.

Your original order

1. POC: create one Announcer applet in Test, using whichever method step 1 points to.
2. Copy Test → PROD: the main payoff, and the mapping table built here gets reused in step 3.
3. DrawIO/Visio import.

Claude Desktop clicking through the browser is fine for exploring once, but I wouldn't use it for building plans: it doesn't do the same thing every time, which is too risky for PROD.
